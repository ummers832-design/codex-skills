# 页面样例与自查

## 微型示例：赛事项目列表中的负责人

以下为虚构演示，不作为任何客户事实。

不充分的写法：`owner | string | 负责人`。

更明确的草稿写法：

- 业务字段：项目负责人。
- 展示：人员姓名；内部人员标识仅用于关联，不直接展示。
- 来源：项目人员关联；具体人员来源待需求负责人确认。
- 未分配：显示“未分配”；有人员关联但姓名不可取得：显示“姓名缺失”。这些文案属于候选规则，确认后使用。
- 筛选：若已确认支持负责人筛选，候选显示姓名，使用人员标识关联；候选数据范围按权限确认，不新增组织通讯录能力。
- 验收：关联存在时能识别负责人；无姓名时不能显示 UUID 或编造姓名。

## 操作例子

不充分：点击归档，提示“已归档”。

更明确：仅有权限且满足已确认归档条件时可操作；成功后项目状态和列表按业务规则更新；失败保留原状态并说明原因。能否归档、归档影响和是否二次确认需要依据需求，不能由这个例子直接决定。

## 三类标记

- 客户材料／已有确认规则：有实际来源。
- AI 建议／待需求负责人确认：合理补充，但尚未批准。
- Mock 示例：仅为演示的值，不是数量上限、真实绩效或能力承诺。

## 交付前检查

### 范围与来源

- 简版模块都能在详细版找到对应位置；详细版新增能力有确认依据。
- 客户陈述、需求负责人建议、AI 推断、确认结论没有混为一谈。
- 已确认的“不包含”没有丢失；未知没有被写成确定承诺。
- 缩减详细 PRD 时，所有模块和关键限制均保留。

### 字段和状态

- 人名、部门和业务状态对客户可读；缺失和真实零值区分。
- 同一字段的含义、来源和状态规则跨页一致。
- 统计口径、日期、金额以及关键默认值有依据或待确认标记。
- 多对象／多版本独立状态不被一个演示全局变量替代。

### 页面与交互

- 页面、区块、弹窗和跳转关系明确，目标编号确实存在。
- 关键操作有条件、权限、实际结果及失败处理。
- Mock 能描述核心业务的模拟状态变化，不只是点按钮弹提示。
- 加载、空值、错误与长文本规则足以指导 UI，不擅自扩展支持终端。

### 交接与完成

- 表结构、索引及 API 设计交由技术方案，不把页面字段直接当数据库列。
- 未运行UI 设计工具、浏览器或真实接口时不声明已验证这些产物。
- 无需求负责人明确确认时，文档仍为草稿；格式认可不等于业务批准。
- 固定 PRD 保持原文，后续变化进入五项变更正文。
- 检查发现的问题先修订草稿或列明待确认，不用“检查通过”掩盖未解决项。
