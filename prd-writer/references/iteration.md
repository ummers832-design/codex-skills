# 需求迭代与版本

## 三种修订路径

1. 草稿：依据新证据同步修订客户版、简版、详细版和技术版，记录实质差异；仍保留未决事项，不自行升级为已确认。
2. 固定基线：原文保持固定，为每项变化生成独立五项变更记录。已批准的变更可进入“当前需求视图”，该视图是派生工作文档，不替代签约或固定 PRD。
3. 用户明确要求重定基线：另建新版本草稿，保留旧固定版并关联变更。只有明确确认新版本后才标记新固定基线，不能伪造相关负责人或客户批准。

如果不知道文档是否固定，先读取元数据及已有确认记录。无法确定时保留原文、另建修订提案，询问必要状态，不擅自覆盖。

## 处理每次变化

- 对照固定 PRD、已确认变更和当前草稿，识别新增、删除、修改、替换、延期、恢复、取消及纯澄清。重复提交同一变化时复用既有记录并追加证据，不重复新增需求。
- 客户未再次提及某功能不代表删除；明确删除也不自动证明其决策权限或商务批准。冲突、撤回、否决和已批准的业务状态分别记录。
- 删除保留需求编号及删除原因，列出受影响页面、权限、数据、依赖和验收条件。历史数据处理不因功能删除而默认物理删除。
- 修改和替换同时写变更前后行为；延期标明本期移出与目标期（未知待定）；恢复引用原需求并重新确认依赖和有效范围。
- 影响分析覆盖客户版说明、简版范围、详细版页面或非 UI 能力、字段、状态、跨模块依赖、验收及技术方案／开发规格 交接。技术工作量、费用、工期缺乏依据时待评估。
- 按五项模板输出原要求、新要求、影响范围、确认结论、验收条件。仅批准部分纳入生效视图，提议、待评估、已否决、已撤回不混入生效范围。
- 多项已批准变更冲突时保留最后无争议的有效状态，列出冲突请需求负责人澄清；不能仅凭时间排序自行解决权限或商务争议。

## 轻量文件与台账

沿用项目命名；无约定时可用：

```text
docs/requirements/
  sources.md              材料、证据、问题与需求映射
  prd-customer.md         客户可读版，关联相同范围与版本
  prd-brief.md            简版；固定后不可覆盖
  prd-detailed.md         详细版或模块总索引；固定后不可覆盖
  prd-technical.md        技术需求与总体约束
  functional-breakdown.md 功能、依赖与批次；需要拆分时创建
  changes/CHG-001.md      有实际变更才创建
  change-log.md           有迭代才创建
  current-requirements.md 需要汇总当前有效范围时创建
```

无需为每次措辞调整复制全套文档。重大版本另存文件；如项目已有版本管理则沿用，不另造强制版本语义。

变更台账建议列：变更编号、类型、需求编号、基线版本、来源、状态、确认依据、影响章节、验收编号、是否已纳入当前视图。状态可为提议／待评估／待确认／已批准／已否决／已撤回／已实施；批准和实施分开记录，批准不等于代码已完成。

当前需求视图写清：基线版本、纳入的已批准变更、截至何次输入、简版有效范围、详细规格变化、已移除需求及未决提案。每个有效条目可追溯到基线或变更；重新生成同一输入时不制造重复变更。同步本地记录不等于已同步需求管理系统或项目文档仓库。

## 迭代验收

- 四份文档对同一需求的范围及确认依据一致；各自的评审状态如实记录；详细版没有未获批准的扩展混入已确认范围。
- 已删除或延期能力不继续出现在本期有效页面、操作、演示路径或验收中；保留必要历史说明和删除记录。
- 受影响依赖、入口、编号引用和验收已更新，无孤立链接。
- 原固定版未改写，待确认提案未覆盖当前有效规则。
- 交给 SDD 的依据明确为固定 PRD 加已确认变更，或新的已确认基线；草稿与候选细节不冒充实现依据。

客户版迭代时用业务语言写清本次新增、减少、调整及对客户使用和交付的影响；不暴露内部任务编号，也不能省略关键范围变化。客户版固定后同样保留旧版，以变更说明或新的讨论稿表达变化。

技术范围变化同步评估功能拆分、依赖顺序、批次 SDD、数据迁移及验证要求；功能拆分和 SDD 的细则见 [功能拆分与分批 SDD 衔接](functional-breakdown.md)。
