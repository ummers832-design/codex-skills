# 技术 PRD：技术需求与总体约束

技术 PRD 面向技术负责人、开发和测试，把业务需求转为可设计、可拆分、可验证的技术需求。它说明系统必须具备什么能力、受什么约束、如何判断满足要求；批次 SDD 再决定具体表字段、接口报文、索引、代码结构和迁移步骤。

先读取 [默认技术框架与工程约束](technical-baseline.md)，将其写入技术 PRD 的“默认技术框架与项目适配”章节。技术框架是开发基线，数据授权、实际资源及具体选项仍按项目确认。

## 编写原则

- 读取客户版、简版、详细版、现有技术资料及已确认变更；列出实际可获得的版本，缺失或未确认时照实注明。
- 以稳定需求编号关联业务目标、技术需求、后续功能和验收。技术文档不能暗中扩大业务范围；必要的工程支撑与新增业务能力分开说明。
- 区分已确认约束、候选方案、待验证假设和未知。技术负责人评审技术可行性，需求负责人确认业务语义，已有确认不重复索取。
- 没有现有系统资料时可写逻辑架构候选，技术框架默认沿用技术基线；模型厂商、数据库引擎、实际资源与基线未指定的服务不得擅自补为已选定。提出具体选型时依据项目材料和实际验证；需要时查证官方资料，不凭空声称支持容量或性能。
- 业务范围未确认也可以编制技术讨论稿或可行性问题清单；有决策影响的未知不能假装已经解决。未确认内容不能作为可编码 SDD 基线。

## 推荐结构

1. 元信息：版本、状态、依据、技术确认记录、范围与非目标。
2. 业务到技术映射：业务需求编号、技术需求编号、技术能力、约束、验收编号及确认状态。
3. 默认技术框架与项目适配，以及系统边界与逻辑架构：输入、输出、模块职责、调用关系、外部依赖与系统边界；已有系统优先复用。
4. 数据与生命周期：核心实体、关键业务属性、关系、来源、所有权、版本、更新、保留与删除要求。不要把页面字段直接当物理数据库列。
5. 系统交互与接口能力：用途、调用方、权限、主要输入输出、异步或同步语义和第三方可用性；完整报文与路径留到 SDD。
6. 权限与数据隔离：身份来源、对象与字段访问边界、授权校验、敏感信息处理；未知权限写待确认，不自行扩展权限管理产品。
7. 适用的非功能要求：容量、吞吐、延迟、并发、可靠性、恢复、成本、可观测性和运维要求。数字有来源才写成目标，否则列测量方案和待定指标。
8. AI 专项（项目涉及才写）：解析与证据来源、候选召回与确定性约束、模型输出校验、低可信或失败处理、模型与数据版本、评测集和效果口径。AI 分数不当作业务事实。
9. 异常与恢复：失败分类、重试、幂等、取消、部分成功、一致性与回滚要求；按实际风险选用。
10. 技术验收与验证计划：前提、动作、可观察结果、指标定义、测试数据、执行环境、预期证据及未完成验证。
11. 风险、待确认决策与拆分建议：影响、验证办法、责任；明确哪些会阻塞后续批次。

小项目可合并章节，不用不适用内容填充篇幅。技术 PRD 不替代详细业务 PRD、商务承诺或实际测试结果；默认不部署、不编码、不修改数据库。
