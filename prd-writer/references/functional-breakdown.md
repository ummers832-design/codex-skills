# 功能拆分与分批 SDD 衔接

在技术 PRD 之后拆功能，再结合实际可用的 `sdd-batch` skill 编写 SDD。拆分的目标是得到可执行、可验收、有依赖关系的工作单元；不是把文档标题改成任务名称。

功能拆分与 SDD 交接同时继承技术 PRD 中的默认框架及已确认偏离；不因拆任务重新选择另一套框架。

## 功能与批次

为功能分配稳定编号，如 `FUNC-001`；沿用项目现有编号。每个功能记录：业务价值或必要工程目的、上游业务与技术需求、触发及输入、可观察输出、范围与非目标、数据和权限、依赖、验收条件、所属批次、阻塞项与状态。负责人和估时没有依据则待定，不编造安排。

将功能组为可验收业务路径，如“提供文件 → 得到解析结果 → 查看证据与错误”；不要只分为前端、后端、数据库三个彼此无法验收的批次。必要的权限或公共能力可作为前置批次，但不能借拆分增加未批准的业务模块。

列明依赖与实施顺序。建立 `业务需求 → 技术需求 → 功能 → 批次 → SDD → 验收及证据` 映射，核查无遗漏、重复或孤立任务。功能可跨多个批次，但各批交付边界要明确。变更时保留删除或拆分编号及关联历史。

## 加载实际 SDD skill

优先使用用户指定的 `sdd-batch` 路径，或本次会话可用技能中的实际路径；不要把用户本机绝对路径写死在可分发 skill 中。找到后读取 `SKILL.md`，以及其批次模板和编码前检查清单，沿用项目已有目录与工作流。其输出中的内部机构名称不需要复制到新产物，以通用职责说明责任。

未找到时可继续完成技术 PRD、功能拆分和 SDD 交接材料；说明尚未应用该 skill，并询问位置或资源。不声称按其规则写完，不擅自安装、覆盖或改写另一 skill。

## 按 sdd-batch 执行

1. 判断变更是否需要 SDD。新增业务逻辑、数据结构、权限、公共能力或跨模块风险通常需要；纯文字等小改动不机械造文档。
2. 先做整体规划，明确总体数据关系、公共能力、依赖、批次和任务顺序。按所加载 skill 的规模规则复核；当前 `sdd-batch` 要求单批目标不超过 1 人周、3 个新增表和 5 个新接口，无法估计时标记未验证，不能宣称符合门限。
3. 为规划批次创建其要求的目录和证据目录。先详细展开当前批次，后续批次先留范围、依赖和待定项，随已验证结果细化，不一次虚构全部实现细节。
4. 当前批次按实际模板写范围与非目标、业务规则、完整数据模型及迁移、接口契约、权限和数据归属、验收、风险与回滚、跨批次依赖、实现及验证任务。
5. 检查需求依据和确认状态、数据库变更、接口支撑、权限、公共能力、迁移及回滚风险、验收与证据。技术 PRD 不自动替代项目已要求的其他技术约定；缺少依据应指出。
6. 影响本批实现的未知未解决时，交付明确标记的 SDD 草稿或准备稿及阻塞清单，不编造字段或接口完成状态，不声明可开发。可以继续不依赖这些问题的其他文档工作。
7. 由承担该批任务的开发人员评审确认后进入实现。只写规格不等于已实现或已验收；证据目录为空不能算测试通过。

发现未确认的第三方限制、核心实体或数据归属变化、费用工期边界或跨系统归属冲突，返回相关需求／技术决策评估，不让当前批次自行扩大基线。

## 迭代联动

需求增加、减少、替换或延期后，评估四版 PRD、功能、依赖、批次、SDD 和验收影响。仅已确认变更更新有效基线；已固定文件保留。已实现批次产生后续变更批次；未开始批次按新依据修订并保留记录。移除功能时同时处理入口、数据、接口消费者和原验收，不能默认删除历史数据。
