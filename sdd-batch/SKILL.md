# sdd-batch — 分批 SDD 开发规范骨架

> 这个 skill 是**结构骨架**，不是公司原文。每次使用前确认：
> 公司具体条款（字段、约束、命名、流程细节）以你公司最新开发手册为准。

## 优先识别：新建规格还是修改已有任务

用户提出修改需求时，先读取 [任务定位、范围判断与文件修订](references/task-change-workflow.md)，优先沿用 PRD skill 已拆分的功能、任务与批次。不要每次重写一套 SDD，也不要要求用户重新提供已可读取的任务清单。

工作顺序：理解变化 → 读取原始 PRD 与已确认变更 → 定位任务及文件正文 → 逐项判断原始范围和当前有效范围 → 修改允许范围内的对应内容 → 同步依赖与 SDD → 检查并报告。

范围内变更直接处理；超原始范围必须提醒，有实际扩展批准则引用后继续，无批准先给明确差异与修改提案；无法判断时说明缺失依据。用户已明确授权纳入的扩展不反复询问。混合变更继续处理不依赖未决扩展的范围内部分。默认只修订任务／规格文件，不自动编码或执行迁移。

## 1. 何时需要写 SDD

按改动的**业务含义和影响**决定，不按代码行数机械判断。

| 改动类型 | 处理方式 |
|---|---|
| 文案、颜色、间距等简单修改 | AI 直接修改并针对性验证，开发人员 review 结果；**不新建 SDD** |
| 已有规格下的局部修复 | 沿用原规格，**不重复创建 SDD**；验证修复及直接影响 |
| **新增或改变业务逻辑、数据结构、权限、公共能力** | **创建或更新相应 SDD**，AI 生成 → 开发人员 review 确认 → 实现 |
| **性能 / 安全 / 合规 / 审计 / 跨模块数据迁移**（无新业务逻辑） | **也要写 SDD**；按影响范围（不是按业务路径）切片 |

> **边界判不清时**：问自己"改坏了能不能 1 人日内回滚"。不能 → 写 SDD。
>
> **反模式**：为套用模板而给简单修改也造一份 SDD；或反过来"为效率"绕过业务逻辑 / 安全 / 权限变更的规格。

## 2. 分批 SDD 的三阶段流程

| 阶段 | 谁做 | 产出 |
|---|---|---|
| **开始开发前**（整体规划） | AI + 开发人员 | 根据 PRD、内部 SOW、已确认变更，梳理模块、依赖、核心数据关系、公共能力、任务顺序 |
| **开始一批任务前**（分批规格） | AI 用 **OpenSpec** 生成本批规格与任务 | 字段、接口、交互、验收条件；由**承担任务的开发人员** review、指挥修订并确认 |
| **本批完成后** | AI + 开发人员 | 验证实际结果，检查跨模块影响，再展开下一批 |

### 分批粒度

- 优先按**一条可验收的业务路径**划分。例：新建 → 保存 → 列表显示 → 查看详情，**DB / 接口 / 前端一起验证**
- **规模门限**：单批目标 ≤ 1 人周、≤ 3 个新增表、≤ 5 个新接口；超出必须再切
- 登录、权限等**公共能力**可作为独立前置任务
- 跨批次依赖**提前标明**（数据契约、状态码、共享枚举值）
- 后续批次的细节随已验证结果展开，**不能脱离整体规划逐项临时决定架构**

### SOW 上浮规则

OpenSpec 阶段若发现以下任一情况，**停下，先回到 FDE**：

- 之前 SOW 阶段未确认的第三方接口限制
- 之前 SOW 阶段未覆盖的核心实体或数据归属
- 涉及报价 / 工期 / 合规边界的变更
- 跨系统的数据所有权冲突

## 3. SDD（OpenSpec 本批规格）必含内容

贵司不用"10 段章节模板"，而是用**编码前规格确认清单**作为最小集合。逐条核对，未解决前不进入编码。

完整清单见 [references/batch-spec-checklist.md](references/batch-spec-checklist.md)；可复制的空白模板见 [references/openspec-template.md](references/openspec-template.md)。

要点速览：

1. 本批需求覆盖完整，**范围与非目标**清楚，依据可定位
2. 已读取**固定详细 PRD / 内部 SOW / 已确认需求变化**
3. 数据库设计变更摘要（新增表 / 修改字段 / 原因 / 功能影响）已阅读
4. 数据字段与实体关系正确，字段类型、约束等满足本批业务
5. **接口**能支撑页面字段及操作，包括可读姓名等数据来源
6. **权限、数据归属、异常反馈**明确
7. 公共能力、前置依赖、对其他模块的影响已检查
8. 数据库迁移风险（删除数据 / 字段改名 / 类型变化 / 历史数据转换）已标记并 review
9. **验收条件**可检验实际结果，OpenSpec 任务覆盖实现 + 验证



### OpenSpec 目录约定（**先建好再填内容**）

项目根目录下建议如下骨架。**所有子目录从一开始就建好**（哪怕暂时是空的），不要等"用到时再建"。

```
project/
├── docs/
│   ├── openspec/
│   │   ├── overall-plan.md           整体规划（见 §2 阶段 1）
│   │   ├── batches/
│   │   │   ├── batch-1/              第 1 批（按整体规划提前建空目录）
│   │   │   │   ├── spec.md           OpenSpec 规格
│   │   │   │   ├── tasks.md          任务清单
│   │   │   │   ├── evidence/         验收证据（截图 / 压测 / 抽样对账）— 提前建空目录
│   │   │   │   └── notes.md          过程中的非正式记录（可空）
│   │   │   ├── batch-2/
│   │   │   └── ...
│   │   ├── changelog.md              跨批次变更记录
│   │   └── sow-link.md               内部 SOW 链接 / 引用
│   └── prd/                          详细 PRD（已固定版本）
├── src/
└── ...
```

**为什么要先建空目录**：
- CI / 自动化脚本能用 glob 找到所有 `batches/batch-*/evidence/`，不会因为某批没建目录就跳过
- 新人进项目立刻看到完整批次的鸟瞰图，不用边走边问"这批在哪"
- 评审人 / FDE 抽查时目录结构是稳定的，不会因为"上批刚建"打乱查阅习惯
- 防止"边做边建"导致路径不一致、引用断裂

**与 OpenSpec 模板对应**：每批的 `spec.md` 按 [openspec-template.md](references/openspec-template.md) 的 9 节填写；`evidence/` 收 §5 列出的 6 类证据；`tasks.md` 跟踪实现+验证。
## 4. SOW vs OpenSpec 分工

| 内容 | 签约前的**内部 SOW** | 编码前的**OpenSpec** |
|---|---|---|
| **数据库** | 核心实体、主要关系、关键字段、数据归属、权限隔离等约束 | 完整字段、类型、必填、默认值、唯一约束、索引、迁移方案 |
| **API** | 核心接口清单、用途、调用方、权限、主要输入输出；**第三方接口的可用性和限制** | 完整请求与响应字段、校验、错误码、分页、幂等 |

不要在 SOW 阶段穷尽全部实现细节，**也不能把重大可行性问题留到开发时**。OpenSpec 阶段**触发上浮条件**见 §2「SOW 上浮规则」。

## 5. 责任与确认边界

- **AI**：生成规格、设计、代码、**自查结果**；所有开发检查由 AI 实际执行
- **开发人员**：review 报告与证据、指挥 AI 修改并**自己确认**结果
- **FDE**：写内部 SOW；记录业务需求变化到需求管理系统（如 Multica.ai）
- **负责人**：不定期抽查 SDD；不逐项审批日常 SDD
- **老板**：把关 Showcase、内部 SOW、报价、正式上线；不逐项审核日常开发 SDD
- **完成后的 PRD 不改写**；新需求作为变更任务独立记录

### 完成定义（"证据"长什么样）

> AI 宣称完成 ≠ 完成。**完成必须由可复核的证据定义**。

| 类型 | 可接受的证据（任选 1+） |
|---|---|
| 单元 / 集成 / E2E 测试 | 测试报告 + 覆盖率；失败的测试不能有 |
| 手工验证 | 屏幕录像 / 截图 / 操作日志（带时间戳） |
| 性能 | 压测报告（QPS / P99 / 错误率） |
| 数据迁移 | 迁移前后行数对账 + 抽样验证 |
| 回滚演练 | staging 环境 upgrade + downgrade 实跑记录 |
| API | 接口响应样例（请求 + 响应 + 错误码） |

> 反模式：仅"我跑了一下没问题" / 仅"代码已合入" — 不算证据。

## 6. 检查的执行位置

- **合并前检查**：由 AI 在开发环境运行，开发人员 review 结果与证据
- **不在流水线上处理**（流水线只跑既定的发布检查）
- 小改动只验证改动及直接影响；DB / 权限 / 核心业务 / 公共组件按实际影响扩大范围
- **适用检查通过、证据齐全即停止**，不为"再保险"重复检查
- 新改动 / 检查失败 / 具体遗漏 → 补查；修复后复查失败项和受影响部分

## 7. 使用本 skill 的工作方式

1. 收到需求 → 若是已有任务修改，先执行任务修订流程；再按 §1 判断是否需要新建或更新 SDD
2. 需要 → §2 三阶段；不需要 → 直接进入任务模板，记录改动与验证
3. §3 清单逐条对照，**未解决前不进入编码**（空白模板见 [references/openspec-template.md](references/openspec-template.md)）
4. §4 对照本批涉及的 DB / API 范围，确认 SOW / OpenSpec 边界
5. §5 明确各角色在本批的责任；§5 子表对每条"完成"声明追问证据
6. 本批完成后 → 走 §6 检查 → 展开下一批

## 8. 常见反模式（不照搬其他项目约定）

- 不能因为"常见"就默认纳入新模块、外部接口、批量导入导出
- 不能让多个独立成果的审核状态共用一个全局布尔值
- 不能以内部 ID 替代客户可读姓名
- 不能用演示成功或置信度当真实效果保证
- 不能在没分清业务字段来源时直接进页面（先有数据，再有页面）
- 不能"理论上能回滚"——回滚必须演练，留下记录
- 不能用 AI 自我宣告"完成"代替证据
- 不要因为"暂时没内容"就漏建子目录 — 目录结构从一开始就是稳定的契约
